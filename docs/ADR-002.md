# ADR-002: CNCF-Graduated Gateway API Implementation Selection

**Status:** Proposed
**Date:** 2026-05-16
**Reviewed:** 2026-05-17 (multi-agent expert review)
**Authors:** Platform Engineering
**Deciders:** Platform Engineering Lead, Engineering Manager
**Relates to:** ADR-001 (API Gateway Platform Selection)

---

## Context

ADR-001 determined that Kong Konnect is not viable long-term and that the platform requires a self-managed, open-source API gateway. This ADR applies a tighter constraint set to select the specific implementation:

- **CNCF Graduated** — the project must have achieved CNCF Graduation, demonstrating production adoption, multi-vendor governance, and sustained maintenance. Sandbox and Incubating projects are excluded as they carry governance and longevity risk.
- **Kubernetes Gateway API conformant** — configuration must be expressed as standard Kubernetes Gateway API resources (GatewayClass, Gateway, HTTPRoute, etc.), not proprietary CRDs, to eliminate implementation lock-in.
- **No vendor lock-in** — the chosen implementation must be Apache 2.0 or equivalent licensed, with multi-vendor governance. Commercial distributions must be optional, not required.
- **AKS compatible** — must run as a standard Kubernetes workload on AKS without requiring unsupported cluster configuration changes.

These constraints are intentionally strict. The goal is a platform foundation that can be maintained and replaced without commercial dependency for the next 3–5 years.

### What "CNCF Graduated" means in this context

CNCF has three maturity levels: Sandbox, Incubating, and Graduated. Graduated and Incubating projects are considered stable and are used successfully in production environments. Graduation specifically requires demonstrated production adoption at scale, committers from multiple independent organisations, and a sustained contribution cadence. It is CNCF's signal that a project is suitable for the Early Majority — i.e., organisations like this platform team, not just early adopters.

For this decision, only Graduated projects are in scope. One explicit exception is documented below.

### Constraint exception: Envoy Gateway

Envoy Gateway is not an independently CNCF Graduated project. It is a sub-project of the CNCF Graduated Envoy Proxy project. CNCF maturity levels apply to top-level hosted projects only; sub-projects do not inherit their parent's classification.

This ADR grants an explicit exception for Envoy Gateway for the following reasons:

1. **Envoy Proxy is CNCF Graduated** with multi-vendor governance and an Apache 2.0 license — the same governance and licensing protections the constraint is designed to enforce.
2. **Multi-vendor steering committee** — Envoy Gateway has active steering committee participation from Tetrate, Alibaba, VMware/Broadcom, Ambassador Labs, and Fidelity Investments.
3. **CNCF endorsement in production** — In April 2026, CNCF itself migrated its own internal services cluster from ingress-nginx to Envoy Gateway, the clearest possible signal of CNCF's confidence in the project's production readiness.
4. **Purpose fit** — Envoy Gateway is the officially endorsed Kubernetes-native control plane for Envoy Proxy and the closest implementation to a vendor-neutral reference for north-south Gateway API traffic.

This exception should be revisited if Envoy Gateway is submitted to CNCF as an independent project.

## Option Analysis

### Option 1 — Envoy Gateway

Envoy Gateway is the official Kubernetes-native control plane for Envoy Proxy. It emerged from a consolidation of efforts by Tetrate, Ambassador Labs, VMware (Contour), and others to provide a vendor-neutral alternative to the fragmented ecosystem of competing Envoy-based ingress controllers.

Envoy Gateway reached its **1.0 production-ready release on March 13, 2024**. As of May 2026, the project is at **v1.8.0** with a stable 6-month minor release cadence.

**Conformance status:** Envoy Gateway is listed as **Partially Conformant** on the official Gateway API implementations page, with its most recent conformance report submitted against v1.4.0. The current Gateway API specification release is v1.5.0. This is notable — Traefik, Cilium, and Istio all have more current conformance reports. In practice, Envoy Gateway's fast-moving release cadence means conformance report submissions lag the actual implementation. The conformance lag should be tracked, and this ADR should be revisited if Envoy Gateway does not submit a v1.5.0 conformance report within two Gateway API release cycles.

**Capability assessment for this platform:**

Envoy Gateway takes a batteries-included approach — offering built-in support for authentication, authorization, rate limiting, CORS handling, header manipulation, and more, exposed through familiar Kubernetes-style APIs. Specifically:

- `SecurityPolicy` *(Envoy Gateway extension: `gateway.envoyproxy.io`)* handles JWT validation, OIDC integration, and mTLS.
- `BackendTrafficPolicy` *(Envoy Gateway extension: `gateway.envoyproxy.io`; overlaps with the standard Gateway API Experimental resource of the same name)* handles rate limiting, circuit breaking, retries, and timeouts.
- All natively, without plugins or additional licensing.

> **Note on API portability:** `SecurityPolicy`, `ClientTrafficPolicy`, and `EnvoyPatchPolicy` are Envoy Gateway proprietary extensions under the `gateway.envoyproxy.io` API group — they are not part of the standard Kubernetes Gateway API specification. See the Consequences section for portability implications.

**Multi-tenant pattern:** Per-namespace GatewayClasses with `SecurityPolicy` and `BackendTrafficPolicy` scoped per `HTTPRoute`. Rate limiting is global and Redis-backed, supporting per-JWT-claim tenant scoping.

> **Known issue — rate limiting listener scope (GitHub #8707):** An unresolved issue filed April 2026 documents that `BackendTrafficPolicy` global rate limiting applies only to the **first listener configured on a Gateway resource**. Additional listeners on the same Gateway do not have rate limiting applied. This must be validated as resolved before relying on per-listener rate limiting in production at the 100-tenant scale. **Recommended mitigation:** deploy one Gateway resource per tenant namespace rather than using multi-listener Gateways.

**AKS compatibility:** Deploys as a standard Kubernetes workload — a controller pod plus Envoy proxy pods provisioned per Gateway resource. No CNI-level changes required. Compatible with Azure CNI and with the platform's existing Cilium CNI. At 100 tenants with one Gateway per namespace, plan for 100 EnvoyProxy deployments; with HA (`replicas: 2`), that is 200 proxy pods — size node pools accordingly.

**Extension model:** Custom logic can be expressed via Lua scripts (added in v1.5 via `EnvoyExtensionPolicy`), WASM filters (Go or Rust), or ext_proc external processors. Lua provides a lower entry barrier for simple header manipulation and transformations. WASM is required for stateful or complex processing. The team should assess Lua first before investing in WASM development.

**Governance:** Multi-vendor (Tetrate, Alibaba, VMware/Broadcom, Ambassador Labs, Fidelity Investments, and others). Apache 2.0 licensed. Tetrate Enterprise Gateway (TEG) provides a commercially supported distribution but is entirely optional — the upstream is fully functional without it.

**Commercial support options:**

The Envoy Gateway project maintains an official enterprise support page at `gateway.envoyproxy.io/contributions/enterprise_support/` listing vendors who provide professional support, training, and consulting. The primary offering at time of writing is Tetrate Enterprise Gateway for Envoy (TEG).

TEG provides 24/7 enterprise support and enablement plus FIPS-verified and CVE-protected builds of Envoy Gateway suitable for mission-critical applications and regulated environments including FedRAMP.

Key characteristics of the TEG commercial offering:

- TEG is 100% upstream Envoy Gateway with no proprietary API forks for core routing and policy configuration — adopting TEG does not introduce lock-in; migrating away from TEG to vanilla Envoy Gateway requires only a change in image source for core configuration
- TEG 1.7.0 is a FIPS-verified distribution of Envoy Gateway 1.7.1, including critical security patches and bug fixes. The recommended upgrade window from TEG 1.6.x to 1.7.0 closes September 1, 2026, indicating an active patch cadence and defined EOL windows per release
- TEG includes optional Coraza WAF integration via a TEG-specific `ExtendedSecurityPolicy` CRD. This CRD is not present in upstream Envoy Gateway — teams adopting Coraza WAF via TEG should account for re-expressing WAF configuration if migrating back to the open-source upstream.
- FIPS-verified and FedRAMP-ready builds are available for tenants with compliance requirements in regulated industries

**Commercial support recommendation for this platform:**

The platform does not require TEG to proceed with the PoC or initial migration. The open-source Envoy Gateway upstream is fully functional and appropriate for the dev environment and initial tenant migrations. TEG becomes relevant under two conditions:

1. **Compliance requirements:** If any tenant operates in a regulated environment (financial services, healthcare, government) that requires FIPS-verified binaries or FedRAMP-ready infrastructure, TEG provides a supported path without requiring a different gateway product.
2. **CVE response SLA:** If the organisation has an internal SLA for CVE remediation (e.g., critical CVEs patched within 72 hours), TEG's CVE-protected builds with early access to security patches provide a contractual guarantee that the upstream community cannot.

For the current platform profile — 100 tenants across AKS, no stated compliance requirements, internal engineering team capable of tracking upstream releases — the open-source upstream is the appropriate starting point. TEG should be evaluated as a commercial procurement decision if either condition above applies to the tenant base.

**Verdict:** Strongest feature-to-requirement match. Purpose-built for the north-south API gateway use case. No operational coupling to other cluster subsystems. Commercial support available via TEG without core configuration lock-in if required.

### Option 2 — Cilium Gateway API

Cilium is the platform's existing CNI. It is a CNCF Graduated project responsible for building networking, security, and observability for cloud-native environments using eBPF. Its Gateway API implementation uses Cilium's per-node embedded Envoy proxy to handle L7 traffic.

**Conformance status:** Cilium is listed as **Conformant** at v1.5.1 on the official Gateway API implementations page — the most current Gateway API conformance of any candidate in this evaluation. Both the Gateway and Mesh profiles are conformant.

**The AKS constraint is a hard blocker.** AKS's "Azure CNI Powered by Cilium" mode locks Cilium configuration and does not expose controls for enabling the Gateway API feature. Microsoft's documented position is that customers requiring more control should use AKS BYO CNI and install Cilium manually. The platform runs Azure CNI Powered by Cilium as a managed service. Switching to BYO CNI requires cluster recreation and is a significant infrastructure change that is out of scope for this decision.

Even setting the AKS constraint aside, Cilium's Gateway API has functional gaps for this use case. For L7 traffic, Cilium's eBPF performance advantage disappears — the processing is handled by its embedded Envoy proxy, not the eBPF kernel path. Advanced auth (OIDC, JWT-scoped rate limiting) and global rate limiting with Redis are not yet natively supported at the same maturity level as Envoy Gateway.

Upgrading the Cilium gateway implementation often implies upgrading the CNI itself, which is a high-risk operation affecting all cluster traffic. Coupling the API gateway upgrade lifecycle to the CNI upgrade lifecycle introduces unacceptable blast radius for a 100-tenant platform.

**Verdict:** Disqualified on AKS compatibility grounds. The platform cannot enable Cilium Gateway API without significant cluster architecture changes. Even if unblocked, the feature maturity gap and CNI coupling are disqualifying for a production multi-tenant gateway.

### Option 3 — Istio (as Gateway API implementation)

Istio is a CNCF Graduated service mesh that implements the Kubernetes Gateway API for both north-south ingress and east-west mesh traffic. It is a conformant Gateway API implementation.

**Conformance status:** Istio is listed as **Conformant** at v1.4.0 on the official Gateway API implementations page, for both the Gateway and Mesh profiles.

**Capability assessment:** Istio fully supports JWT auth, OIDC (via RequestAuthentication), rate limiting (via integration with ext_authz or Envoy rate limit service), and mTLS. The feature set is complete for this platform's requirements.

**Operational overhead:** Istio is a full service mesh, not a gateway. Even in Ambient mode (sidecarless), it introduces a ztunnel DaemonSet, a waypoint proxy per namespace, and its own control plane (istiod). The operational surface is substantially larger than needed for north-south gateway functionality alone. The team has no existing Istio experience, and troubleshooting Istio's traffic management layer is materially more complex than Envoy Gateway's purpose-built gateway model.

**Feature coupling risk:** In Ambient mode, EnvoyFilters are not supported, and VirtualService is only at Alpha level — leaving the Gateway API as the only supported option, while some richer Envoy-specific functionality is not yet accessible. This creates a capability gap compared to Envoy Gateway's native SecurityPolicy and BackendTrafficPolicy extensions.

**Governance:** Multi-vendor (Google, IBM, Solo.io, and others). Apache 2.0. The project has strong governance but a history of rapid breaking changes that have affected operators in past releases.

**Verdict:** Not selected. The capability match is adequate, but the operational surface is significantly larger than required for the north-south API gateway use case. The team would absorb full service mesh operational complexity to solve a gateway problem. Istio remains a valid future consideration if a service mesh is adopted for east-west traffic.

### Note: Traefik — addressed for team members with existing familiarity

Traefik is a widely used, capable API gateway and ingress controller with strong Kubernetes support and a large community. Several platform team members have prior experience with it, and it merits an explicit explanation of why it was not carried forward as a candidate.

**Conformance status:** Traefik Proxy is listed as **Conformant at v1.5.1** on the official Gateway API implementations page — the most up-to-date conformance report of any implementation evaluated in this ADR, including Envoy Gateway. It fully supports all HTTPRoute core and extended features, BackendTLSPolicy, GRPCRoute, TLSRoute, and TCPRoute. On conformance alone, Traefik is among the strongest implementations in this field.

**Traefik is not a CNCF project.** It is maintained by Traefik Labs, a commercial company, under an MIT license. It has never been submitted to CNCF at any maturity level (Traefik Labs is a CNCF Silver Member, but corporate membership does not confer project governance protections or multi-vendor oversight). This is the disqualifying constraint under this ADR's selection criteria — not a reflection of Traefik's technical quality or conformance standing.

The CNCF Graduated requirement exists specifically to protect against single-vendor control of the platform's critical path. Traefik Labs controls the Traefik roadmap, release cadence, and licensing entirely. The MIT license protects against proprietary lock-in at the code level, but the project has no multi-vendor governance model, no CNCF technical oversight committee, and no requirement for committers from independent organisations. If Traefik Labs changes direction commercially — as many infrastructure companies have — there is no governance backstop.

**If the CNCF constraint were relaxed, Traefik would be a competitive option.** Its genuine strengths include full Gateway API v1.5.1 conformance, a strong conformance contribution history across multiple Gateway API releases, same-day support for new Gateway API releases, and a middleware model familiar to teams coming from Nginx or HAProxy. However, two capability gaps are relevant to this platform specifically:

- **Advanced auth in open source.** Native first-party OIDC and JWT validation middleware is a Traefik Hub commercial tier feature. The capability is achievable in open-source Traefik v3 via the JWT plugin or `forwardAuth` integration with an external identity provider, but this requires additional operational surface not present in Envoy Gateway's native `SecurityPolicy`. Teams requiring native out-of-the-box parity without integration complexity would need Traefik Hub, replacing one commercial dependency (Kong Konnect) with another.
- **Route update latency.** Production data (Rivet Engineering, June 2025; gateway-api-bench project) shows Traefik can take 1–2 seconds to propagate route changes under load, compared to milliseconds for Envoy Gateway. For a platform continuously reconciling CRD changes across 100 tenants, this latency compounds.

> **Note on Traefik open-source rate limiting:** Traefik Proxy v3.4 added distributed Redis-backed rate limiting as a built-in open-source feature. This capability is not behind the Hub commercial tier.

Prior Traefik experience on the team is an asset if Traefik is ever reconsidered — the learning curve is low and the operational model is familiar. But under the constraints this ADR applies, it does not qualify.

### Note: Azure Application Gateway for Containers — addressed for AKS-native bias

Azure Application Gateway for Containers (AGC) is Microsoft's managed Gateway API implementation for AKS. It is a reasonable question to ask whether a natively Azure-managed product would simplify operations on an AKS platform. This note explains why it was not selected.

**Conformance status:** AGC is listed as **Stale** on the official Gateway API implementations page, with its last conformance report submitted against Gateway API **v1.1.0**. The current Gateway API specification is v1.5.0 — AGC is four minor versions behind and has not submitted a conformance report for any version since v1.1.0. Under the Gateway API page review policy, implementations that remain Stale through successive review cycles will be removed from the implementations list. This is a significant signal: Microsoft has not kept AGC's Gateway API conformance current while the standard has continued to evolve.

**AGC fails three of the four selection constraints simultaneously.**

**CNCF Graduated:** AGC is a Microsoft Azure proprietary service, not a CNCF project at any maturity level. It is not open source and has no multi-vendor governance.

**No vendor lock-in:** AGC requires Azure-specific GatewayClass references and, depending on deployment mode, Azure ARM resources that are non-portable:

- In **BYO mode**, the Azure Frontend and Association ARM resources must be provisioned manually and have an independent lifecycle from Kubernetes — deletion of the Kubernetes Gateway resource does not trigger ARM resource cleanup.
- In **ALB-Controller-managed mode** (the recommended deployment path), the ALB Controller reconciles ARM resource lifecycle against Kubernetes Gateway lifecycle, reducing the manual lifecycle burden.

In both modes, Gateway resources referencing the AGC GatewayClass and any AGC-specific annotations are Azure-proprietary and non-portable. Migrating away from AGC requires replacing these Gateway-layer resources regardless of deployment mode. Standard HTTPRoute resources using core Gateway API fields are largely portable to other conformant implementations.

**AKS portability:** AGC is AKS-only by design. It cannot run on any other Kubernetes distribution, on-premises cluster, or alternative cloud. The platform's stated goal is a gateway foundation viable for 3–5 years without commercial dependency — AGC deepens Azure dependency rather than reducing it.

**Gateway API conformance is partial.** AGC's last conformance report covers Gateway API v1.1.0. Standard rate limiting and auth features available in the current specification are not supported. AGC provides an Azure WAF integration via a proprietary `AzureSecurityPolicy` resource (preview as of late 2025), but this is an Azure-proprietary mechanism that deepens vendor dependency rather than providing portable security policy.

**The operational simplicity argument does not hold at this platform's scale.** The managed data plane model has real benefits — no in-cluster proxy pods to version or resource-provision, Azure SLA coverage, and native Azure Monitor integration. However AGC introduces concrete scale limits that negate these benefits at 100 tenants:

- Maximum of **200 routing rules per AGC instance** — multi-instance deployment would be required at this platform's rule count
- A dedicated **/24 subnet** (254 usable IPs) per AGC instance — requires pre-provisioned Azure networking
- **ARM API rate throttling** under high configuration churn — 100 tenants continuously reconciling routes generates sustained ARM API load

For a platform team already operating AKS, ArgoCD, and a full GitOps stack, an in-cluster Envoy Gateway deployment is simpler to reason about and debug than a split cluster/ARM control plane at this scale.

AGC may be appropriate for teams with simpler requirements, a single-tenant workload, and a strategic commitment to Azure-native tooling. It is not appropriate for this platform.

## Decision

**Adopt Envoy Gateway as the API gateway platform.**

Envoy Gateway is the only candidate that satisfies all four constraints — either directly or via the documented CNCF Graduated exception — while providing native support for the platform's L7 requirements (OIDC, JWT-scoped rate limiting, mTLS, per-tenant policy isolation) without plugins, additional licensing, or coupling to other cluster subsystems.

## Consequences

### What this enables

- A fully open-source, Apache 2.0 licensed API gateway with no commercial dependency at any scale
- Configuration portability for standard resources: `HTTPRoute` and `BackendTrafficPolicy` (standard Experimental) are Kubernetes Gateway API specifications — migration to a different conformant implementation requires only a GatewayClass swap for routing configuration
- Native OIDC, JWT validation, mTLS, and Redis-backed global rate limiting — the capabilities that required Kong Enterprise — are available in the open core
- Standard Kubernetes workload deployment on AKS — no cluster architecture changes required
- Multi-vendor governance reduces the risk of upstream abandonment or adverse commercial decisions
- Tetrate Enterprise Gateway (TEG) provides an optional commercial support contract with CVE-patched and FIPS-verified builds — available if compliance requirements or CVE SLAs require it — without introducing core configuration lock-in

### What this forecloses

- **Cilium Gateway API consolidation.** A future in which the CNI and the API gateway are the same component (fewer operational concerns) is foreclosed by AKS's managed Cilium configuration constraints. This may be revisited if AKS adds managed Cilium Gateway API support.
- **Lua plugin ecosystem.** Kong's Lua plugin model is not available. Custom logic for complex stateful processing requires WASM (Go or Rust) or ext_proc external processors. For simple transformations, Lua scripting (available via `EnvoyExtensionPolicy` since v1.5) is an accessible entry point. The team should evaluate Lua before investing in WASM development.
- **Rapid operator reuse.** The existing custom operator emits Kong declarative config. It must be rebuilt to emit Gateway API resources (`HTTPRoute`, `SecurityPolicy`, `BackendTrafficPolicy`). This is a material engineering investment but produces a cleaner architecture — ArgoCD owns reconciliation, the operator generates declarative intent.

### New problems this creates

**SecurityPolicy portability.** `SecurityPolicy` is an Envoy Gateway proprietary extension (`gateway.envoyproxy.io`), not a standard Gateway API resource. If the platform migrates to a different Gateway API implementation in the future, auth configuration expressed in `SecurityPolicy` must be re-expressed in the target implementation's equivalent API. This is a lower migration cost than rewriting all routing configuration, but it is not zero-cost portability.

**Rate limiting listener scope bug.** GitHub issue #8707 (filed April 2026, unresolved) documents that `BackendTrafficPolicy` global rate limiting applies only to the first listener on a Gateway. The recommended architecture (one Gateway per tenant namespace) avoids this issue by using single-listener Gateways. Validate that this issue is resolved or mitigated before deploying multi-listener Gateways.

**Operator rebuild scope.** The operator must be rebuilt from scratch, not retargeted. The effort is estimated at 2–3 sprints for a senior Go developer. The architectural result — the operator generates Kubernetes resources,  ArgoCD reconciles them — is strictly better than the current model but requires upfront investment.

**Short-term Konnect cost.** The Konnect bill continues during migration. Commercial renegotiation with Kong must run in parallel to reduce cost while Envoy Gateway is built out.

**Redis operational dependency.** Global rate limiting in Envoy Gateway requires an external Redis instance. The platform already operates Redis for other purposes; this is a configuration concern rather than a new dependency. Plan for Redis HA — rate limiting fails open if Redis is unavailable.

**Release cadence tracking.** Envoy Gateway follows a 6-month minor release cycle with defined EOL windows. The platform team must track releases and plan upgrades. TEG's commercial offering provides a defined CVE SLA if the team cannot maintain a continuous upgrade cadence.

### Migration sequencing

1. Immediate: Initiate Kong commercial renegotiation to reduce Konnect cost during migration window
2. Sprint 1–2: Envoy Gateway proof-of-concept — validate OIDC, JWT rate limiting, and multi-tenant HTTPRoute isolation on a non-production tenant in the existing AKS cluster; validate GitHub #8707 status and confirm single-Gateway-per-namespace architecture
3. Sprint 2–4: Operator rebuild — generate `HTTPRoute`, `SecurityPolicy`, `BackendTrafficPolicy` resources per tenant CRD instance
4. Sprint 4–5: Infrastructure — Helm chart, Kustomize base, ArgoCD ApplicationSet, Cilium NetworkPolicy for gateway pods
5. Sprint 5–9: Wave-based tenant migration (dev → staging → production) with traffic shadowing at the Application Gateway layer
6. Sprint 9+: Konnect decommission

## Operational Overhead: In-Cluster Gateway vs. Kong Konnect SaaS

This section provides a direct comparison of the operational model the platform team currently operates under (Kong Konnect SaaS) against the model this ADR adopts (Envoy Gateway in-cluster). The purpose is to make the ongoing cost of ownership explicit before committing to the migration, and to establish realistic expectations for the engineering team and management stakeholders.

### Current State: Kong Konnect SaaS Operational Model

Kong Konnect is a hosted SaaS control plane. The operational division is:

| Responsibility | Kong (SaaS) | Platform Team |
|---|---|---|
| Control plane availability and upgrades | ✅ Kong manages | — |
| Data plane (Kong Gateway pod) upgrades | — | ✅ Team manages |
| CVE patching (control plane) | ✅ Kong manages | — |
| CVE patching (data plane) | — | ✅ Team manages |
| Config distribution and consistency | ✅ Kong manages | — |
| Analytics, audit logs, developer portal | ✅ Included in contract | — |
| Incident response (control plane) | ✅ Kong SLA | — |
| Incident response (data plane / routing bugs) | — | ✅ Team manages |
| Plugin updates (Lua) | — | ✅ Team manages |
| Capacity planning | — | ✅ Team manages |

**Estimated annual platform team overhead under Konnect:** 15–25 hours/year for a 100-tenant platform in steady state. The control plane, persistence, config distribution, and analytics are entirely off the team's plate. The team's gateway operational effort is limited to data plane upgrades, plugin changes, and routing configuration. Konnect's managed model is operationally lean — the cost is the licensing, not the labour.

---

### Proposed State: Envoy Gateway In-Cluster Operational Model

With Envoy Gateway, the platform team owns the entire stack. Every operational responsibility Kong currently absorbs becomes a team obligation.

| Responsibility | Envoy Gateway (upstream) | Platform Team |
|---|---|---|
| Control plane availability | — | ✅ Team manages (HA replicas, PDB) |
| Control plane upgrades | Releases; 6-month minor cadence | ✅ Team plans and executes |
| CRD upgrade lifecycle | Releases; versioned separately | ✅ Team manages (separate ArgoCD Application) |
| Data plane (proxy pod) upgrades | Released with controller | ✅ Team manages per-Gateway |
| CVE patching | Community releases patches | ✅ Team applies within internal SLA |
| Redis (global rate limiting backend) | Not managed | ✅ Team owns HA and failover |
| Observability (metrics, dashboards, alerts) | Metrics exposed; no dashboards | ✅ Team builds and maintains |
| Incident response (all layers) | Community support only | ✅ Team owns end-to-end |
| Config distribution | Kubernetes reconciler (built-in) | — |
| Developer portal / analytics | Not included | ✅ Team builds or foregoes |
| Capacity planning | — | ✅ Team manages (proxy pod sizing per tenant) |

### Estimated Time Commitment by Activity

The following estimates are based on a 100-tenant AKS platform running Envoy Gateway v1.8.x in steady state (post-PoC, post-migration). They assume one Senior Infrastructure Engineer as the primary gateway operator, with occasional involvement from a second engineer.

#### Upgrade Cycle (per minor release — every ~6 months)

Envoy Gateway follows a 6-month minor release cadence. Each minor release requires a coordinated upgrade of the CRD chart, the controller Helm chart, and validation of the proxy fleet.

| Activity | Estimated Time |
|---|---|
| Read release notes, changelog, breaking changes | 1–2 hours |
| Upgrade dev environment (CRDs + controller) | 1–2 hours |
| Validate existing Gateways, HTTPRoutes, SecurityPolicies in dev | 2–3 hours |
| Validate operator-generated resources still reconcile correctly | 1–2 hours |
| Upgrade staging; soak period | 2–3 hours |
| Upgrade production (wave-based) | 2–4 hours |
| **Total per minor release** | **9–16 hours** |
| **Annual (2 minor releases/year)** | **18–32 hours** |

TEG (Tetrate Enterprise Gateway) reduces this burden by providing a defined upgrade window (e.g., TEG 1.6.x → 1.7.0 by September 1, 2026) and pre-validated builds, at the cost of a commercial contract.

#### CVE and Security Patch Management

Envoy CVEs are published to the `envoy-announce` mailing list. Depending on severity, response timelines vary.

| Severity | Typical Response Target | Estimated Time to Patch |
|---|---|---|
| Critical | 24–72 hours | 4–8 hours (test + staged rollout) |
| High | 1–2 weeks | 3–6 hours |
| Moderate/Low | Next scheduled upgrade | 0 additional hours |

Historical Envoy CVE frequency: approximately 3–6 security advisories per year, of which 1–2 typically require out-of-band patching at Critical or High severity.

**Estimated annual CVE management overhead:** 8–18 hours/year.

> **Note:** TEG's CVE-protected builds provide early access to patches before public CVE disclosure, which is the primary value proposition if the organisation has a defined CVE SLA (e.g., critical CVEs patched within 72 hours).

#### Redis Operational Overhead

In-cluster Redis (PoC) requires minimal maintenance. Production Redis (Azure Cache for Redis via ESO) requires:

| Activity | Estimated Time |
|---|---|
| Initial production Redis HA configuration | 4–8 hours (one-time, Sprint 4–5) |
| Quarterly health check and capacity review | 1–2 hours |
| Failover testing (annual) | 2–3 hours |
| Incident response for Redis outage | 1–4 hours per event |
| **Estimated annual steady-state overhead** | **6–12 hours/year** |

> **Fail-open reminder:** If Redis is unavailable, rate limiting passes all requests. This is correct Envoy Gateway behavior and is not an incident requiring escalation — but the team must document it to prevent unnecessary on-call escalations during Redis maintenance windows.

Incident response overhead depends heavily on incident frequency and complexity. The following is a baseline estimate for a stable platform.

| Incident Type | Frequency (estimate) | Estimated Time per Incident |
|---|---|---|
| Proxy pod crash / OOM | 2–4x/year | 1–2 hours |
| Route reconciliation stall (controller) | 1–2x/year | 1–3 hours |
| Rate limiting anomaly (Redis-related) | 1–2x/year | 1–2 hours |

| Major incident (gateway-wide outage) | 0–1x/year | 4–12 hours |
| **Estimated annual incident response overhead** | | **12–28 hours/year** |

Unlike Kong Konnect, where control plane incidents are Kong's responsibility, every Envoy Gateway incident is the platform team's responsibility end-to-end. Debugging requires familiarity with Envoy proxy configuration, Gateway API reconciliation behaviour, and Kubernetes control plane interactions — a steeper debugging surface than a SaaS control plane where vendor support absorbs the investigation.

#### Capacity and Scaling Management

At 100 tenants, each with one Gateway resource, the proxy fleet is 100 EnvoyProxy deployments (200 pods at HA settings). Growth beyond 100 tenants requires:
- Node pool capacity review
- Resource request/limit tuning per-proxy
- Review of control plane replica count and resource sizing

**Estimated annual capacity planning overhead:** 4–8 hours/year.

### Pros and Cons: In-Cluster vs. SaaS

#### Advantages of In-Cluster Envoy Gateway

**Operational transparency.** Every configuration change is a Kubernetes resource in Git — reviewed, audited, versioned, and rolled back via ArgoCD. There is no "what did someone change in the Konnect UI" class of incident. The gateway configuration is the source of truth and it lives in the same GitOps repository as everything else on the platform.

**Debugging access.** The team has full access to control plane logs, proxy access logs, metrics at the millisecond granularity, and Envoy's admin API. When a routing issue occurs, the team can debug end-to-end without waiting for vendor support or filing a ticket to access logs held by a third party.

**No external SaaS dependency.** Envoy Gateway has no runtime dependency on an external service. If the internet connectivity from the cluster degrades or a vendor's API is unavailable, the gateway continues serving traffic from its last reconciled state. Kong Konnect's control plane dependency means a Konnect outage can affect config propagation.

**Cost predictability at scale.** Envoy Gateway has no per-tenant, per-request, or per-API licensing model. Adding tenant 101 costs no more than tenant 100. Kong Konnect pricing typically scales with API calls, services, or seats — the cost model is less predictable at growth.

**Portability.** The platform is not tied to Kong's SaaS infrastructure, Kong's API format, or Kong's roadmap. If the team needs to migrate clusters, adopt a different cloud, or swap the gateway layer in 3 years, the configuration is standard Gateway API resources (for routing) with documented proprietary extensions (for auth). The migration surface is bounded.

**No commercial dependency for core functionality.** OIDC, JWT rate limiting, mTLS, and multi-tenant policy isolation are all in the open-source upstream. The capabilities that currently require a Kong Enterprise contract are available at no additional cost.

#### Disadvantages of In-Cluster Envoy Gateway

**Full operational ownership.** The team absorbs everything Kong currently manages: upgrades, CVE patching, HA configuration, control plane health, Redis management, and incident response. This is a real and ongoing engineering cost that must be staffed and sustained. If the primary gateway operator leaves the team, operational continuity is at risk unless knowledge is documented and spread.

**Steeper incident debugging.** Envoy Gateway's debugging surface is significantly more complex than a SaaS control plane where vendor support absorbs investigation. Debugging a Gateway API reconciliation issue requires understanding Kubernetes controller mechanics, Envoy xDS configuration, and the Envoy Gateway control loop. This is a non-trivial operational competency that takes 3–6 months to build on a new team.

**No built-in developer portal or analytics UI.** Kong Konnect includes a developer portal, API analytics, and a management UI used by tenant teams to self-serve API documentation and access keys. Envoy Gateway provides none of this. If tenant teams currently depend on the Konnect portal, a replacement must be evaluated (this is out of scope for the PoC but must be addressed before the Konnect decommission).

**Upgrade discipline required.** With a 6-month minor release cadence and defined EOL windows, the platform team must maintain upgrade discipline. Falling behind (e.g., running a version past its EOL) means running without CVE patches. Teams that deprioritise upgrades under operational pressure can accumulate upgrade debt that becomes a large, risky catch-up effort.

**Redis adds operational surface.** Global rate limiting requires an external Redis instance. Kong Konnect's rate limiting is handled by Kong's infrastructure — the team does not own a Redis cluster today. Azure Cache for Redis reduces the management burden but adds cost and a new monitoring obligation.

**SecurityPolicy is not portable.** Auth configuration expressed in Envoy Gateway's `SecurityPolicy` extension cannot be directly ported to another Gateway API implementation. If the platform ever needs to replace Envoy Gateway, auth policies must be re-expressed in the target implementation's API. This is a lower migration cost than a full config rewrite, but it is not zero.

**Initial investment is substantial.** The PoC, operator rebuild, and migration are estimated at 9+ sprints of engineering work before the team reaches steady state. This is a significant upfront investment that defers the operational savings.

---

### Recommendation

The operational overhead of running Envoy Gateway in-cluster is real and should not be understated. The migration is financially viable only if the Konnect licensing savings exceed the net additional engineering labour cost, and only if the team has the capacity and competency to sustain the operational model at steady state.

The following conditions should be confirmed before committing to the full migration:

1. **Konnect licensing cost exceeds break-even.** The annual Konnect contract cost should exceed the estimated net additional overhead (£2,250–£8,500/year at steady state) by a meaningful margin — ideally 3–5x — to justify the migration investment and risk.
2. **Team capacity is staffed for the first year.** The first year of operations (PoC + migration + initial steady state) will require approximately 150–250 hours of Senior Infrastructure Engineer time beyond normal platform work. This must be budgeted, not assumed to absorb into existing capacity.
3. **Operational runbooks are produced during migration.** Upgrade procedures, CVE response runbooks, Redis failover procedures, and incident debugging guides must be written as part of the migration work — not deferred to "when we need them."
4. **Developer portal replacement is planned.** If tenant teams use the Konnect portal, a replacement strategy must be defined before Konnect is decommissioned. This is a separate workstream and should not block the PoC, but it blocks the final Konnect decommission (Sprint 9+).
